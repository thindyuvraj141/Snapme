# Snapme 💬

A Snapchat/WhatsApp-style app: snaps, a Feed, Memories and chats. Frontend: GitHub Pages (`index.html`). Deploy: GitHub Actions. Backend: Firebase (free Spark plan: Authentication + Firestore). Optional Android app built by GitHub Actions (Capacitor).

## Snapme layout (24 Oct): Snap · Feed · Circles · Add friend · Profile (Memories are on the Profile since Round 15)
The app was rebuilt to look and work like the SnapTime demo. The old chat features are all still there (they live under **Circles > Chats** and in the Profile tab).
- **Header:** the name *Snapme*, a 🔥 **Day Streak** pill (days in a row you posted a snap) and a chat button (red dot = unread chats).
- **Snap tab:** camera (the old mood chips were removed in Round 14; you write a caption on the Share screen instead), a **10-second voice vibe** (mic button), **dual capture** (one tap takes the back and then the front camera, two photos in one snap), flip button. There is **no timer**. After the shot you get a preview: choose the audience (**Friends** or **Inner Circle**) and press **Post**.
- **Feed tab:** “Today’s Raw Feed” with two views: **Friends** (snaps of your friends) and **Public** (snaps of Public accounts). Snaps stay in the Feed for 30 days (Round 14; before that 24 hours). Reactions (🔥 / ❤️), ⋮ menu: Add as friend, Report, Hide, Delete (own snaps).
- **Who sees a snap = account level.** A **Public** account’s snaps (audience Friends) also show in everybody’s Public feed. A **Private** account’s snaps are shown to friends only (switch: Profile tab > Public account, or Settings > Privacy & Security > Private account). Inner Circle snaps never go public.
- **Circles tab:** Friends and Chats (switch at the top), requests badge, search, the Add friend page and the Friends map. A ★ on a friend adds them to your **Inner Circle** (private list, only you can read it).
- **Memories (Time Capsule):** every snap you **post to the Feed** is also kept in your Memories (picture, caption, voice vibe); a picture that is only taken with the camera is never saved. Since Round 15 they are shown **on the Profile page** (Instagram style, **Photos** and **Tagged** icon tabs) and are **never removed automatically**. Tap to open, 🗑 to delete.
- **Profile tab:** photo, name, Public/Private switch, Edit profile, Chats, Add friend, Friends map, Settings.
- **Removed:** the Avatar maker (and its admin switch). Everything else stayed. The package id, repo, site URL and Firebase project did not change.
- **Rules:** publish the new `firestore.rules` (adds `posts` and `users/<uid>/memories`). Without it posting shows an error.
- **Admin panel:** the switch “Avatar maker” is now **“Snaps & Feed”** (stops new snaps). Reports about a snap show **Open snap** / **Remove snap**; the Claude tab has `remove_snap`. Upload the new `panel.html`.
- **Clean-up job:** `scripts/delete-expired-accounts.js` (the daily Action) now also deletes snaps 24 h after they ended, a deleted account’s snaps, and notifications older than 30 days. Memories are **not** deleted by the job any more (Round 15).
- **Honest limits (free Firebase plan):** (1) a snap is a compressed picture saved *inside* Firestore (about 60–120 KB, two photos for dual capture), so lots of snaps use the free 1 GiB storage and 10 GiB/month reads faster than text chats. (2) The **Public** view shows an arbitrary subset (up to 60 snaps of the day): Firestore cannot sort a public query for a free app without a manual index, so it is *not* newest-first or “most popular”. (3) Dual capture takes the two photos one after the other, not at the same instant. (4) The camera and microphone need permission; in the browser they work only on the https site. (5) Real Firestore, real phones and the GitHub job were not available here: all of this was tested with a simulated Firebase and phone (`qa/t_sm_snap.py`, 64 checks), so the first real try may need one small correction.
- After uploading `index.html` open **Settings > App update** (or reopen the app) to get the new screens; the APK needs a rebuild only for the new name / icon (Actions > Build APK).

4. The support email `VVaultweb@gmail.com` is already set in `index.html`, `privacy.html`, `terms.html` and `delete-account.html`. Change it in those four files if you want another address.

## How the app works
- Create an account with name, username, email and password. Friends find you by username.
- Public accounts can be added directly. A **private account** must receive a friend request first; messages flow only after it is accepted. After an **unfriend**, the chat is deleted for both people and a new request is needed to chat again.
- Blocked people cannot see your username, email, photo or online status. Unblocking keeps the friendship.
- (Removed 25 Oct, Round 11: there is no app lock and no fingerprint lock any more.) App lock (Profile > Settings > Safety & Visibility): asks for your account password every time the app is opened. **Fingerprint unlock** is a second switch there: it needs the newest APK and at least one fingerprint saved in the phone's own Settings. After 2 failed fingerprint tries the account password unlocks the app. Everything is stored only on the phone.
- You can change your username once in a while; the old one is retired forever.
- Messages are deleted automatically. Set it per chat from the chat's ⋮ menu > **Auto-delete**: **After seen** (one-to-one chats only: the message is deleted about 10 seconds after the other person sees it), **Today** (24 hours) or **7 days**. The default for new chats is in Settings > Chat Style. There is no backup.
- Photos and videos can be saved to the phone: open one and tap **Save**, or use the chat's ⋮ menu > **Photos & videos · save**. (The Android app saves into the gallery; the website downloads the file.)
- **Re-publish `firestore.rules` after this update.** It adds the `locs` rule used by the Friends map. Until it is published, turning on location sharing shows “Please publish the latest Firestore rules”.
- (Before 24 Oct) The round neon button on the Chats tab opened the camera; now the camera is the **Snap** tab. (25 Oct: the round camera button is gone from the Chats page, and **New group** is no longer in the ⋮ menu; groups that already exist keep working.)
- Settings > **Share Snapme** shares the GitHub Releases page `https://github.com/thindyuvraj141/VText/releases` (where the APK is published) with your username.
- Profile page: the **Background** button puts a gallery photo or a colour style behind your profile photo (saved on your profile, only you see it). **Settings** is the last section of the Profile tab (below Account). Under your photo the Name / Username / Save card edits your name; tap Username to change it.
- **Friends page = Friends + Requests.** (Before 24 Oct the bottom bar was Friends · Chats · + · Location · Profile; now see “Snapme layout” above: the same pages are reached from Circles and Profile.) “My friends” is on top, then a divider, then “Friend requests” (Accept / Decline) and “Sent requests” (Cancel). The red request counter sits on the Friends button.
- **Location page (Friends map)** — the pin button in the bottom bar. A dark neon map shows your friends who share their location, with their photo, how far away they are and when they were last seen; the people-button opens the “Friends nearby” list (within 5 km first). Sharing is **off by default** and is only started after a consent card. You can share with all friends or selected friends, exact or approximate (about 1 km), and stop any time. People you blocked or unfriended never see you. Your position is saved in the Firestore collection `locs` (one document per person, deleted when you stop sharing, log out or delete the account). Location is updated **only while Snapme is open** (no background tracking, so no “always allow” permission is needed). Map pictures (tiles) come from OpenStreetMap (free, **no API key needed**, needs internet; the credit is shown on the map). If a tile does not load, OSM France and then Esri are tried automatically. (CARTO was used first but now demands an API key, so it is not used any more.) OpenStreetMap's rules are for light use like a friends app; if Snapme ever gets very many users, switch to a paid tile service with your own key (change `LOC_TILES` in the code).
- **Permission screen:** after sign-in Snapme asks once for Camera, Gallery (photos/videos) and Location. It can be opened again from Settings > **App permissions**. The Android permission dialogs need the **new APK** (the website alone only asks for camera and location through the browser).
- Deleting your account now has **7 days to change your mind** (see the 22 Oct section).

  Honest limits: a person gets no extra message on day 6 (a free app cannot send emails); the reminder is the date shown when deleting and again when logging in. Deleted data is removed by the job, so it can take up to a day after the 7 days. Until the secret is set, nothing is deleted after the 7 days (the account just stays blocked). Re-publish `firestore.rules` (new `photos` and `xpt` rules).

- **Expo Push (free, open source service by Expo) – switched OFF until you add a Project ID.**
  What it does: the sender’s phone tells Expo’s free push service about a new message, Expo wakes the other phone through Google’s FCM (Expo uses FCM underneath; like every Android push it does **not** arrive after *Force stop*). Your push token is kept in `chats/<id>.xpt.<your uid>` – only members of that chat can read it. A **muted** chat has no entry (no push); a **locked** chat only shows “Snapme / New message”. The app’s own notification copy is switched off while Expo Push is registered, so you do not get two.
  **Setup:**
  1. Make a free account on **expo.dev**, create a project (any name) and copy its **Project ID** (a long id like `1b2c3d4e-…`).
  2. In that Expo project: **Credentials > Android**, add the application identifier `com.thindyuvraj.vtext`, then add an **FCM V1 service account key**: upload the same Firebase `.json` key from the delete-account setup above.
  3. In the repo file `config.js` put the id: `window.VT_EXPO_PROJECT_ID = 'your-id';`
  4. `scripts/google-services.json` must be in the repo (Firebase console > Project settings > Your apps > Android `com.thindyuvraj.vtext` > download; see “Push notifications” below).
  5. Upload the new files, publish `firestore.rules`, run **Actions > Build APK**, install the new APK on **both** phones (the sender’s phone makes the call).
  6. Test (changed 27 Oct): the **Expo push** row is no longer in the app. The admin panel (`panel.html`, VetextLogin repo) > Controls > **Push notifications (closed app)** has the on/off switch and the setup notes. With a Project ID in `config.js` and the switch ON, send yourself a message from the other phone and swipe Snapme away: a notification arrives in a few seconds.
  How it fits in: `scripts/android/VTextFcmService.java.tpl` is a small Android service that turns Expo’s “data only” message into a normal Snapme notification (Snapme icon, sound, tap opens the chat) when the app is not in front, and hands everything else to Capacitor’s push plugin as before.
  Honest limits: (1) written and tested with a simulated phone and a simulated Expo server only – the real Android and real exp.host parts could not be run here, so the first real test may need one correction. (2) Pushes are sent by the **Android app**; a message sent from the website/browser makes no Expo push (browsers are not allowed to call Expo). (3) If Expo is on but cannot deliver (for example the FCM key is missing), the app has switched its own notifications off – the **Expo push** row in Settings shows the error; remove the Project ID from `config.js` to go back. (4) The token of a phone that logs out while offline stays in the chats until the next login on that phone. (5) Anyone who is in a chat with you can read your push token there, so in theory such a person could send your phone a fake notification (they can already message you; Expo’s extra token-security option needs a secret on a server, which this free setup does not have). (6) If Snapme’s hidden background page is also running, a message can appear through both ways, but both use the same notification, so it is shown once.

## Admin panel (a separate website, not part of this app)
The admin panel is **not in this repository and not in the app**. It is one separate file (`panel.html`) on its own website, so nothing about it can be found by opening Snapme. The app only contains the small part that obeys it: the switches, maintenance screen, announcement, force-update screen (installed Android app only), blocked words, the verified badge, and the suspended-account screen (with an end time and an appeal form) and the one-time warning. These read one public settings document (`config/app`) and the person's own records (`bans/<uid>`, `appeals/<uid>`, `warnings/<uid>`); only an admin can change them, and that is enforced by `firestore.rules`, not by hiding the page.

- Publish the newest `firestore.rules` (Firebase console > Firestore Database > Rules > Publish). It adds `admins`, `bans`, `appeals`, `warnings`, `adminnotes`, `config`, `reports` and `adminlog`, and the owner's right to give the verified badge.
- The panel, its setup steps and its privacy notes are in the file `ADMIN-SITE-README.txt` that comes with the panel download (keep it on your own phone; it is not part of this repository). Do **not** put the address of the panel into this public repository.
- What the panel can do: suspend / unsuspend users (the person sees the reason and cannot send messages, friend requests or create chats), read the in-app reports and remove the reported message or chat, maintenance mode, 8 on/off switches (Location, Camera, Voice messages, Creating groups, Photos/videos/documents, Snaps & Feed, Adding new friends, New sign-ups), announcements, add / remove moderators, an action log, and a “Claude” tab that runs a list of commands that Claude wrote for you after you check it.
- Honest limits: only **Suspend** (including its end time) is enforced by the server. Maintenance mode, the feature switches, “sign-ups closed”, the blocked words and the minimum app version are enforced by the app, so they stop normal users but not somebody who modifies the app code on purpose. Admins can open only the one message that was reported, never anybody's chats.

## Push notifications (messages when the app is closed)
What is already inside the app (nothing to change in the code):
- **Android app:** the Capacitor plugin `@capacitor/push-notifications` is installed by the APK build, the manifest has the notification permission and the default notification channel/icon, and the app registers the phone with Firebase Cloud Messaging after sign-in. Tapping a push opens that chat.
- **Website / installed web app:** `firebase-messaging-sw.js` (own scope, so `sw.js` is not touched) shows pushes in browsers.
- Each phone/browser saves its token in `users/<uid>/private/push` (only you can read it). Turning notifications off, logging out or deleting the account removes it.
- Settings > Notifications > **Push notifications** tells you the state of this phone (On / Not set up yet / Needs the newest APK / Blocked).

What YOU have to do once (all free except step 4):
1. **Firebase console > Project settings > Your apps > Add app > Android.** Package name: `com.thindyuvraj.vtext`. Skip the other steps, then press **Download google-services.json**.
2. Upload that file to the repo as **`scripts/google-services.json`**. Then run **Actions > Build APK** again and install the new APK. (Without the file the app still works; the Settings row says “Not set up yet”.)
3. *Browsers only (optional):* Firebase console > Project settings > **Cloud Messaging** > Web Push certificates > **Generate key pair**. Copy the key into `config.js` as `window.VT_VAPID = '...'`.
4. **Sending the pushes needs a server.** Firebase's free Spark plan cannot run Cloud Functions, so nothing sends a push yet and the app keeps using its own background notifications. To switch real push on: upgrade the project to the **Blaze** plan (pay-as-you-go; the free quota is far more than this app uses, but a card is needed), then deploy `functions/` (the GitHub action **Deploy push function**: add a secret `FIREBASE_SERVICE_ACCOUNT` containing a Google service-account JSON key, then Actions > Deploy push function > Run). Open `functions/index.js` first and set `REGION` to your Firestore location. Finally set `window.VT_PUSH_SERVER = true;` in `config.js` so the app does not show a second copy of every notification.
- Pushes show the sender's name and the message text (text is cut at 100 characters; photos show “📷 Photo”). Locked chats show only “Snapme · New message”, muted chats stay silent. Set `SHOW_TEXT = false` in `functions/index.js` to hide the text.
- A phone that was force-stopped by the user gets nothing from any app until it is opened again (Android rule).

Push to `main`: `Deploy Snapme` stamps the version (`1.0.<run number>`) into the app. On the phone open **Settings > App update**; the app only updates when you tap it, and the visible version changes.

## Android APK
1. The repo must contain `package.json`, `capacitor.config.json`, `scripts/` (including `vtext-debug.keystore.b64`), `assets/` and `.github/workflows/android.yml`.
2. Actions > **Build APK (test)** > Run workflow. After about 10 minutes `Snapme.apk` is in the repo's **Releases** (right side) and in the run's Artifacts.
3. The APK loads the website, so changing `index.html` does **not** need a new APK. Build a new APK only when native things change (fingerprint, background service, permission dialogs, icons).
4. Every APK has an increasing version code and is signed with the same key, so a new APK installs over the old one. **If you installed an APK built before this key was added, uninstall it once** (the signing key changed), then install the new one.
5. The build tries the full app first; if an optional part (fingerprint plugin or background service) fails, it builds a simpler APK and says so in the release notes.

### Notifications in the background (free plan, no server, no Google push)
Snapme shows a small "running" notification and asks Android to exclude it from battery optimisation. While the app screen exists (even in the background) the normal chat connection delivers the notifications.

**Hidden background page.** When the app screen is gone (you swipe it away, press Back until it closes, or Android closes it to save memory) the background service opens the same Snapme page in a hidden WebView (the address ends with `?bg=1`). That page keeps listening to your chats and asks the service to show the notification; tapping it opens the app on that chat. The hidden page never marks you online, never shows the lock screen and never asks for permissions. It stops by itself when you log out, and it is also started again after the phone restarts or Snapme is updated (only if "Keep running in the background" was on). The code is in `scripts/android/VTextHeadless.java.tpl` and `VTextBoot.java.tpl`.

If this part ever fails to compile, the build script builds the APK again without it and says so in the release notes ("Hidden background page ... NOT included"); everything else still works.

Honest limits (this is true for every app that does not use Google's push): **Force stop** (Settings > Apps > Snapme > Force stop) stops it until you open Snapme once; some phones (Xiaomi, Oppo, Vivo, Realme, Samsung "sleeping apps") close background apps on their own, so allow Snapme in the battery / autostart settings of the phone; with the screen off for a long time Android can delay the connection (usually seconds to a few minutes). Real push for a force-stopped app needs Firebase Cloud Messaging with a server, which Snapme does not use.

## Round 16 (29 Oct): push notifications from the admin panel
Upload: `index.html`, `README.md`, the new `.github/workflows/send-push.yml`, `scripts/build_android.sh` and `scripts/patch_android.py`; in **VetextLogin** upload `panel.html` (and `ADMIN-SITE-README.txt` if you keep it). `firestore.rules` does not change. A new APK is only needed for the Firebase push (run *Build APK* once and read its release notes); the banner and bell part work without it.
- **Send a push to every phone.** Admin panel > **Controls** (owner) > **Push notification**: Title (optional) + Text (up to 300 characters) > **Send to everyone** > confirm. The phones get it within seconds: a **phone notification with the Snapme sound** when Snapme is in the background **or was swiped away** (the Android app keeps a hidden page running that listens, the same way it already shows message and friend-snap notifications), a **banner on top of the screen** when Snapme is open (tap it for the full text, ✕ closes it). Every push is also listed on the **Notifications (bell) page** for 7 days and counts on the bell badge. Tapping the phone notification opens the Notifications page.
- **How it works (free, no server).** The panel writes the push into the public document `config/app` (`pushes`: newest first, the last 5 are kept; **Withdraw** removes one from the list). Every running Snapme already listens to that document (maintenance mode, switches and announcements use it too), so there is no Cloud Function, no Blaze plan, no Expo and no new rule. The phones only read. Code: `patches/js/bcast.js` (app), `panel.html` (`sendPush`, the card, the Claude commands `push` / `push_clear`).
- **Closed apps: real Firebase push (free, through GitHub).** New workflow `.github/workflows/send-push.yml` = **Send push notifications**. Every 5 minutes (also on *Run workflow*, and **at once** when the panel has a GitHub token saved) it reads the waiting pushes from `config/app`, takes the Firebase tokens of all Android phones from `users/<uid>/private/push` and sends the push through Firebase Cloud Messaging (free, no Blaze plan) as a *notification message*: Android itself shows it, **also when Snapme is closed or swiped away**, with the Snapme icon and message channel; tapping it opens Snapme (and the Notifications page). While Snapme is open the page shows its own banner instead. It writes `sent` and `reach` (number of phones) back to the push, which the panel shows under *Sent recently*; a push that Firebase refuses is marked with the reason and is **not** tried again every 5 minutes. A run with nothing to send ends in a few seconds; a run without the secret ends green with a note (no e-mail flood). Needs: (1) the repo secret `FIREBASE_SERVICE_ACCOUNT` (the same JSON key as “Deploy Firestore rules”), (2) `scripts/google-services.json` in the repo (already there) and an **APK that contains the push plugin** (GitHub > Releases > the newest APK notes must say “Push notifications (Firebase): included”; the phone registers itself when Snapme is opened once and notifications are allowed), (3) the *Firebase Cloud Messaging API* enabled for the project (it is by default; if the job says “Requested entity was not found”, open Google Cloud console > APIs & Services > Library > Firebase Cloud Messaging API > Enable). Test: send a push from the panel, swipe Snapme away, wait up to 5 minutes (or 1 minute with the token).
- **Instant sending (optional).** Panel > Controls > Push notification > *Closed apps*: save a GitHub **fine-grained token** (Settings > Developer settings > Personal access tokens > Fine-grained; repository access = only your app repo; permission **Actions: Read and write**) with the repo name. It stays in that browser only (localStorage). *Send to everyone* then also calls GitHub `.../actions/workflows/send-push.yml/dispatches`; *Run the job now* does it without a new push. Without a token the 5-minute schedule does the work.
- **APK build fallback (29 Oct).** If the APK build with the push plugin failed only because Snapme’s own messaging service (`VTextFcmService`) did not compile, the build now retries **with the push plugin and Firebase but without that service** (release notes: “Snapme’s own messaging service: NOT included”). Admin pushes still work when the app is closed (they are notification messages); Expo message pushes need that service. The release notes also list why each earlier attempt failed.
- **Why the APK with the push plugin kept failing (found 30 Oct).** `VTextFcmService` (our messaging service) extends Firebase's `FirebaseMessagingService`, but the app module did not have the Firebase Messaging library on its own compile path (Capacitor's push plugin brings it with `implementation`, which the app cannot see), so the Java step stopped with *package com.google.firebase.messaging does not exist* and every attempt with the push plugin failed (the build then fell back to an APK without push). `scripts/patch_android.py` now adds `com.google.firebase:firebase-messaging` (version of Capacitor 8: 25.0.1) to `android/app/build.gradle` whenever our service is part of the build; the google-services classpath fallback is 4.4.4 (Capacitor 8). The service file was also compiled here against hand-written stubs of the Android / Firebase classes (syntax and types are fine; the real Android build on GitHub is still the final judge). After building, open the release notes: it must say **Push notifications (Firebase): included** and **Snapme's own messaging service: included**.
- **Likes, comments, accepted requests with Expo ON (fixed 30 Oct).** The app hid its own phone notification for everything while Expo Push was registered. Expo only carries messages and snaps, so likes / comments / accepted friend requests lost their background notification as soon as Expo was switched on. They are now always shown by the app (`pushNote(..., true)` in `nfAlert`). Still true: with the app **closed (swiped away)** only messages and friend snaps (Expo) and owner pushes (Firebase job) arrive; a new friend request, like or comment is shown the next time Snapme runs (a free server cannot reach a person who shares no chat with you yet).
- **Messages and friend snaps when closed** use Expo Push (see “Expo Push” above: a free Expo account + the Project ID in `config.js` + the same Firebase key uploaded to Expo). Without it they rely on the hidden background page, which some phones stop when the app is swiped away.
- **Once per phone.** A push is shown once on each phone. A phone that sees this feature for the first time stays silent about older pushes. A push older than 3 days is not announced. With **Show notifications** off in Settings nothing pops up (the push is still on the bell page). Messages and friend snaps are unchanged: they still come from the hidden background page (and from Expo Push when you set it up).
- **Honest limits.** (1) A phone that is switched off or offline gets the push when it is back (up to 3 days). A phone where Snapme was **force-stopped** (Settings > Apps > Snapme > Force stop) gets nothing from any app until Snapme is opened once (an Android rule for every push service); without the Firebase push above (no secret, or an APK without the push plugin) a swiped-away phone only gets it when the hidden background page is alive. (2) The website / installed web app shows it while the page is open (and a browser notification when the tab is in the background). (3) Anybody can read `config/app` (it is public by design), so never write secrets in a push.

Without it the app falls back to reading the first 60 and sorting them on the phone (no Show more), so nothing breaks: if you open Firebase console > Firestore > Indexes and add that composite index (or open the link that the browser console prints on the first failed query), paging works fully.

Only you (🗑 in the viewer) or deleting your account removes a memory. The Feed still keeps each snap for 30 days, then the snap leaves the Feed; its Memories copy stays.
- **Posting safety net (29 Oct).** If Firebase answers “Missing or insufficient permissions” to the post (typically because the newest `firestore.rules` are not published, or an older copy is live), the app no longer just fails: it writes the pieces one by one. The snap is still posted (the caption then travels as the old mood text `vb`, without `cp` / `lt`), the Memories copy is saved with whatever the live rules accept, and the toast says what Firebase refused (“Snap posted ⚡ but Firebase refused: … Publish the newest firestore.rules.”). Test: `qa/t_r15b.py` (11 checks; the fake Firestore has switches `__mock.old` and `__mock.noPost`).
- **Publish the rules from GitHub (29 Oct), no Firebase console editor needed.** New workflow `.github/workflows/deploy-rules.yml` = **Deploy Firestore rules**. It publishes the file `firestore.rules` of the repo root to Firebase with the Admin SDK (`securityRules().createRuleset` / `releaseFirestoreRuleset`), using the same secret as the account-deletion job (`FIREBASE_SERVICE_ACCOUNT`). It runs by itself whenever `firestore.rules` changes on `main`, and by hand: Actions > Deploy Firestore rules > Run workflow (`validate_only` = 1 only checks the file, 0 checks and publishes). Firebase's real compiler checks the file first: a mistake is printed with its line and nothing is published; after publishing the job reads the live rules back and prints `OK: the live rules are exactly the file firestore.rules`. Why: pasting the 28 KB file into the console editor on a phone can corrupt it (the editor's autocomplete / slow input), and an editor error blocks Publish, so the old rules stay live (then every post fails with “Missing or insufficient permissions”). Test: `qa/t_rules_deploy.js` (12 checks, firebase-admin stubbed). If the job answers with a permission error, the service account of the key lacks the right to manage rules: in Google Cloud console > IAM give it the role “Firebase Rules Admin”.

(2) Old memories from before Round 13 have no `o` flag, so other people do not see them on your profile (you do). (3) A snap that tags you is copied into your Memories only while that snap is still in the Feed (30 days). (4) The mock used in the tests cannot evaluate real Firestore list rules or indexes completely.
